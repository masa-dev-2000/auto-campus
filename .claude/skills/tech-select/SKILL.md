# /tech-select — 技術選定 + ADR 自動生成ワークフロー

## 既存 ADR の確認（自動取得）

!`ls docs/adr/*.md 2>/dev/null | grep -v gitkeep | sort || echo "ADR なし（初回）"`

技術の比較検討を行い、決定内容を ADR（Architecture Decision Record）として記録します。
「なぜその技術を選んだか」「なぜ他を選ばなかったか」を残すことで、Claude が将来同じ議論を繰り返さなくなります。

ADR テンプレート参照: @../../templates/adr.md
加重マトリクス参照: @templates/weighted-matrix.md

使い方:
- `/tech-select` — 対話式でカテゴリを決める
- `/tech-select STT プロバイダー` — カテゴリを直接指定
- `/tech-select STT プロバイダー --yolo` — 確認なしで ADR まで一気に生成

---

## 実行モード判定

`$ARGUMENTS` を確認してください:

- **`--yolo` が含まれる場合**: STEP 1 のヒアリングを省略（`$ARGUMENTS` からカテゴリを取得）し、STEP 2〜5 を連続実行。各確認ゲートをスキップして ADR を自動生成・コミット。
- **デフォルト（`--interactive`）**: 各 STEP のゲートで一時停止してユーザー確認を取る。

---

## STEP 1: 選定対象の確認

`$ARGUMENTS` が指定されている場合（`--yolo` フラグ以外の部分）はそれをカテゴリとして使用。
空の場合は以下を聞いてください:

```
どの技術カテゴリを選定しますか？
（例: データベース、認証ライブラリ、STT プロバイダー、デプロイ先、フロントエンドフレームワーク）

候補が既に絞られている場合は教えてください。
```

続けて以下を確認（一度にまとめて）:
```
1. このシステムでその技術が担う役割は？（1文で）
2. 重視する条件は？（速度 / コスト / 学習コスト / 実績 / 日本語情報 から上位3つ）
3. 除外条件はありますか？（例: 有料SaaSは避けたい、Rustは使いたくない）
```

**`--yolo` でない場合**: ここで一時停止。回答を受け取ってから STEP 2 へ。

---

## STEP 2: 候補の調査

`WebSearch` と `WebFetch` で候補技術を調査してください。

**候補の選び方:**
- 業界標準（デファクトスタンダード）を必ず1つ含める
- 新興の有力候補を1つ含める
- 最大4候補まで（多すぎると決断が遅くなる）

**調査観点と情報源:**

| 観点 | 調べ方 |
|-----|-------|
| パフォーマンス | 公式ベンチマーク・独立した比較記事。数値は出典必須 |
| 学習コスト | ドキュメントの質・日本語情報量・Stack Overflow の質問数 |
| コスト | 公式 pricing ページを直接参照。無料枠・従量課金を試算 |
| コミュニティ | GitHub スター数・最終コミット日・Issues の活発さ |
| 要件適合度 | STEP 1 で聞いた「役割」「重視する条件」「除外条件」に照らす |

## STEP 3.5: 加重スコアリング + バイアスチェック

比較表を作った段階で直感的な結論が出やすいが、**後付け正当化を防ぐため加重マトリクスを必ず実行する**。

### 加重スコアリング

1. STEP 1 で聞いた「重視する条件」をもとに評価軸と重みを設定（合計 100）
2. 各候補を 1〜5 でスコアリング
3. 加重合計（Σ 重み × スコア）で順位付け

```markdown
| 評価軸 | 重み | [A] | [B] | [C] |
|--------|------|-----|-----|-----|
| [軸1]  | ...  | ... | ... | ... |
| [軸2]  | ...  | ... | ... | ... |
| **加重合計** | 100 | | | |
```

### バイアスチェック（推奨前に必ず自己採点）

以下のバイアスが混入していないかチェックし、結果を明示する:

- **可用性バイアス**: 最近使ったことがある技術を過大評価していないか
- **権威バイアス**: 「大手が使っているから」を理由にしていないか
- **確証バイアス**: 最初から決めていた答えに有利な観点だけ選んでいないか
- **引用の不均衡**: 採用候補だけ詳細・新鮮なソースで、却下候補は古いソースになっていないか
- **未確認数値**: ベンチマーク・価格に出典なしの数値が混じっていないか

**バイアスが検出された場合**: 該当する評価軸を見直してから推奨を出すこと。

### 推奨（バイアスチェック通過後）

```markdown
### 推奨

**推奨**: [技術A]（加重スコア: XXX点）
**主な理由**: ...（出典: URL）
**主なリスク**: ...
**軽減策**: ...
**バイアスチェック結果**: [問題なし / 〇〇バイアスを修正済み]
```

**`--yolo` でない場合**: ここで一時停止。「この推奨でよいですか？別の選択肢を選びますか？」と確認してから STEP 4 へ。

---

## STEP 4: ADR ファイルの生成

`docs/adr/` のファイル一覧を確認して続番（NNN）を決めてください。

ファイル名: `docs/adr/ADR-NNN-[カテゴリ名].md`

```markdown
# ADR-NNN: [カテゴリ名]の選定

日付: YYYY-MM-DD
状態: 決定済み

---

## 背景

[この技術が必要な理由・解決したい問題を2〜3文で。
「〜という要件があり、〜という技術的選択が必要だった」という形が書きやすい]

## 決定

**採用: [技術名]**

[採用理由を3〜5行。数値があれば含める（出典: URL）]

## 加重スコアリング結果

| 評価軸 | 重み | [A] | [B] | [C] |
|--------|------|-----|-----|-----|
| ...    | ...  | ... | ... | ... |
| **加重合計** | 100 | | | |

## 検討した代替案

### [技術B]
- 概要: ...
- 却下理由: ... ← これが最も重要。具体的に書く

### [技術C]
- 概要: ...
- 却下理由: ...

## 結果として生じるトレードオフ

- **メリット**: ...
- **デメリット・リスク**: ...
- **軽減策**: ...

## 参照

- [公式ドキュメント](URL)
- [比較ベンチマーク](URL)
```

---

## STEP 5: CLAUDE.md と関連ファイルへの反映

ADR を作成したら:
1. `CLAUDE.md` の開発スタックセクションを最新に更新
2. コミットは 1 ファイル 1 コミットの原則で

---

## 注意（ガードレール）

- **ベンチマーク数値は出典なしで書かない**。公式サイトかベンチマーク記事の URL を必ず添える
- **「みんなが使っているから」は理由にならない**。加重スコアで示す
- **却下した選択肢の記録が最も重要**。採用理由だけ書いた ADR は半分しか機能しない
- **STEP 3.5 を省略しない**。バイアスチェックなしの推奨は却下する
- 価格情報は変動するので参照日を記載する
