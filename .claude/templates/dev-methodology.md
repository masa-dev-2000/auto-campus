# 開発プロジェクトの進め方ノウハウ

Claude Code を使ったプロジェクト開発の方法論。随時更新する。

---

## 0→100 タスクテンプレート

どのプロジェクトにも適用できる抽象化されたタスク一覧。
新規プロジェクト開始時にこれをコピーして具体化する。

---

### Stage 1｜探索（0→10）「何を作るか」を決める

**完了条件**: 「このプロジェクトは〇〇のために△△を作る。□□は作らない」と言える状態

#### 1-1. 問いの定義
- [ ] ターゲットユーザーを具体的な1人に絞る（「20代男性」ではなく「週3回会議がある営業職の田中さん」）
- [ ] その人が「今どうやっているか」を書く（現状の解決策・回避策）
- [ ] なぜ現状では不十分かを書く（コスト・時間・品質・精神的負荷）
- [ ] 1文に凝縮する：「〇〇にとって、△△するときの、□□という問題を解く」

#### 1-2. オーナーの目的整理
- [ ] このプロジェクトで得たいアウトカムをすべて書き出す
- [ ] 優先順位をつける（1位が判断基準になる）
- [ ] 「これが達成できたら成功」という最低ラインを決める

#### 1-3. 競合・先行事例調査
- [ ] 同じ問題を解こうとするツール・サービスを5つ以上リストアップ
- [ ] 各ツールの「できること」「できないこと」を表にまとめる
- [ ] 参照できる OSS・類似プロジェクトを GitHub で探す
- [ ] 自分のプロジェクトが埋めるギャップを特定し、言語化する

#### 1-4. 技術的実現可能性の確認（スパイク）
- [ ] 「これが動かなければ全部無意味」な技術的核心を1つ選ぶ
- [ ] その核心だけを確認する最小コードを書いて動かす（UIなし・ハードコード可）
- [ ] 「続ける / スタックを変える / 断念する」を判断する
- [ ] 判断と理由を記録する

#### 1-5. スコープの境界を引く
- [ ] 作る機能リストを書く
- [ ] 「作らないもの」リストを明示する
- [ ] MVP に含まれない機能を「将来リスト」に移す
- [ ] スコープを関係者（自分含む）に共有して合意する

---

### Stage 2｜定義（10→20）「何を作るか」を固める

**完了条件**: SPEC.md ができており、Claude にそれを渡せば実装できる状態

#### 2-1. コア機能の列挙
- [ ] 機能を全部書き出す（ブレスト。まず量を出す）
- [ ] MoSCoW で分類する（Must / Should / Could / Won't）
- [ ] Must のみを MVP に入れる
- [ ] 各機能に「なぜ必要か」を1行で書く

#### 2-2. 各機能の完了条件定義
- [ ] 各機能を「Given / When / Then」の形で書く（例: 「音声入力があるとき、マイクに話すと、1.5秒以内にテキストが表示される」）
- [ ] 曖昧な言葉（「適切に」「正しく」「スムーズに」）を排除する
- [ ] 数値で測れない完了条件は書き直す

#### 2-3. 非機能要件の定義
- [ ] レイテンシ（最大何秒？P50/P95 で定義する）
- [ ] スループット（同時何人まで？）
- [ ] データ保持期間（いつまで？どこに？）
- [ ] 可用性（何%？ダウンタイムは許容できるか？）
- [ ] セキュリティ要件（認証が必要か？データは暗号化するか？）
- [ ] 対応環境（OS・ブラウザ・デバイス）

#### 2-4. 使用シーンの具体化
- [ ] ユーザーが「最初に使う」場面を詳細に描写する（ユーザーストーリー）
- [ ] 「一番よく使う」場面を書く（ハッピーパス）
- [ ] 「問題が起きる」場面を3つ書く（エラーシナリオ）

#### 2-5. 状態・モードの洗い出し
- [ ] システムが取りうる状態を全部書く（Lamport の教え）
- [ ] 状態遷移図を描く（紙でもテキストでも可）
- [ ] 各遷移のトリガー・条件・副作用を書く
- [ ] 「同時に2つのことが起きたら？」を考える

#### 2-6. 未決定事項の管理
- [ ] 決まっていないことを全部書き出す
- [ ] 各項目に「いつまでに決める必要があるか」を書く
- [ ] 決定できる人・情報を特定する

---

### Stage 3｜設計（20→30）「どう作るか」を決める

**完了条件**: コンポーネント図・データモデル・API仕様が文書化されている

#### 3-1. 技術スタック選定
- [ ] 各レイヤー（フロント / バック / DB / インフラ）の選択肢を2〜3個出す
- [ ] 評価基準を決める（学習コスト・エコシステム・パフォーマンス・コスト・チームの習熟度）
- [ ] 選択と理由を ADR（Architecture Decision Record）として記録する
- [ ] 選んだスタックで「Stage 1-4 のスパイク」がまだなければやる

#### 3-2. コンポーネント分解
- [ ] システムを独立したコンポーネントに分割する
- [ ] 各コンポーネントの責務を1文で書く（2つ書きたくなったら分割する）
- [ ] コンポーネント間の依存関係を図で描く
- [ ] 依存の方向が一方通行かを確認する（Uncle Bob の教え: ビジネスロジックは外部依存しない）
- [ ] 各コンポーネントを独立してテストできるかを確認する

#### 3-3. データモデル設計
- [ ] 扱うエンティティ（名詞）を全部書く
- [ ] 各エンティティの属性・型・制約（null 可否・長さ等）を定義する
- [ ] エンティティ間の関係（1対多・多対多）を定義する
- [ ] データのライフサイクル（作成・更新・削除の条件）を書く
- [ ] データの不変条件（Invariant）を書く（例: 「残高は0以上」）

#### 3-4. API / インターフェース設計
- [ ] 各コンポーネントが外に公開するインターフェースを書く
- [ ] 入力・出力の型を定義する（型定義ファイルまたはスキーマとして）
- [ ] エラーケースと返り値を定義する
- [ ] 破壊的変更のルールを決める（バージョニング戦略）

#### 3-5. リスク評価
- [ ] 「ここが失敗したらプロジェクト全体が危うい」箇所を列挙する
- [ ] 各リスクに対策（代替案・軽減策・受け入れ）を書く
- [ ] 特定した全リスクに対してスパイクが必要かを判断する

#### 3-6. ディレクトリ構成の決定
- [ ] フォルダ構成を書く
- [ ] 各フォルダの責務を1行で書く
- [ ] ファイルの命名規則を決める

---

### Stage 4｜環境構築（30→40）「作れる状態」を整える

**完了条件**: `make dev` で起動し `make test` でテストが通る状態

#### 4-1. リポジトリ初期化
- [ ] `git init` または `git clone`
- [ ] CLAUDE.md 作成（スタック・コマンド・規約・禁止事項）
- [ ] `.gitignore` 作成（言語・フレームワーク・OS 別）
- [ ] `.env.example` 作成（必要な環境変数の一覧、値なし）
- [ ] `README.md` の骨格作成（プロジェクト概要・セットアップ手順）

#### 4-2. パッケージ管理の設定
- [ ] パッケージマネージャーの初期化（`uv init` / `npm init` / `cargo init` 等）
- [ ] 直接依存のみを追加する（間接依存は自動管理に任せる）
- [ ] バージョンを固定してロックファイルをコミットする
- [ ] `requirements.txt` / `package.json` / `pyproject.toml` をコミットする

#### 4-3. 開発コマンドの整備
- [ ] 開発サーバー起動コマンドを1つに統一する（`make dev` / `npm run dev`）
- [ ] テスト実行コマンドを作る（`make test`）
- [ ] Lint 実行コマンドを作る（`make lint`）
- [ ] ビルドコマンドを作る（`make build`）
- [ ] README にすべてのコマンドを記載する

#### 4-4. Lint・フォーマッターの設定
- [ ] Lint ツールを設定する（ESLint / ruff / golangci-lint 等）
- [ ] フォーマッターを設定する（Prettier / black / gofmt 等）
- [ ] エディタ共通設定を作る（`.editorconfig`）
- [ ] git pre-commit フックで自動実行する設定を入れる

#### 4-5. テスト基盤の準備
- [ ] テストフレームワークを選定・インストールする
- [ ] テスト実行コマンドを確認する
- [ ] 最初のテストを1本書いて実行できることを確認する（`assert 1 + 1 == 2` レベルで可）
- [ ] カバレッジ計測の設定をする

#### 4-6. CI の設定
- [ ] CI プラットフォームを選定する（GitHub Actions / CircleCI 等）
- [ ] push / PR 時に lint + test が自動で走るワークフローを作る
- [ ] ビルドが通ることを確認する
- [ ] バッジを README に貼る

#### 4-7. シークレット管理の確立
- [ ] `.env` が `.gitignore` に入っていることを確認する
- [ ] シークレットスキャン（`git-secrets` / `trufflehog` 等）を設定する
- [ ] 本番用シークレットの管理方法を決める（環境変数 / Secret Manager 等）
- [ ] CLAUDE.md に「`.env` をコミットしないこと」を明記する

---

### Stage 5｜PoC（40→50）「コアが動く」を証明する

**完了条件**: 「この技術で作れる」が証明されている。または代替策に切り替えた

#### 5-1. コアリスクの特定
- [ ] Stage 1-4 で特定した核心を再確認する
- [ ] 「これが動かなければ全部無意味」という1つを選ぶ
- [ ] なぜそれが核心かを1文で書く

#### 5-2. 最小スパイク実装
- [ ] UI なし・エラー処理なし・ハードコード可で実装する
- [ ] 外部 API との接続を確認する
- [ ] Stage 2 で定義した非機能要件（レイテンシ等）を実計測する

#### 5-3. 判断と記録
- [ ] 完了条件を満たしているかを判断する
- [ ] 「続ける / スタックを変える / スコープを変える」を決める
- [ ] 判断と理由を docs/ に記録する（後で「なぜこうなったか」がわかるように）

---

### Stage 6｜コア実装（50→65）「使えるものができる」

**完了条件**: 設計書通りのコンポーネントが揃い、単体テストが通っている

#### 6-1. 実装順序の決定
- [ ] 依存関係の少ないコンポーネントから順番を決める
- [ ] 1コンポーネント = 1PR を基本とする
- [ ] 各 PR の完了条件を先に書いてから実装を始める

#### 6-2. コンポーネント実装
- [ ] 実装と同時にテストを書く（後回しにしない）
- [ ] インターフェース（型定義・API 仕様）を先に書いてから実装する
- [ ] レビュー（偉人エージェント or 自分で翌日に読む）を通してからマージする

#### 6-3. 単体テストの充実
- [ ] 正常系のテスト（ハッピーパス）
- [ ] 異常系のテスト（例外・エラー）
- [ ] 境界値のテスト（0 / 最大値 / null / 空文字）
- [ ] 外部依存はモックに差し替えてテストする

#### 6-4. エラーケースの実装
- [ ] タイムアウト（API が応答しない場合）
- [ ] 接続失敗（ネットワーク断）
- [ ] 不正入力・バリデーション
- [ ] リソース枯渇（メモリ・ディスク）

#### 6-5. ログの整備
- [ ] 構造化ログ（JSON 形式）の設定
- [ ] ログレベルの定義（DEBUG / INFO / WARN / ERROR）
- [ ] リクエスト ID 等、トレーサビリティの確保
- [ ] 個人情報・シークレットがログに出ないことを確認する

---

### Stage 7｜統合・実用化（65→75）「実際に使える」

**完了条件**: 実際の使用シーンで、完了条件を満たして動く

#### 7-1. エンドツーエンドのシナリオ実行
- [ ] Stage 2-4 で書いたユーザーストーリーを実際に動かす（ハッピーパス）
- [ ] Stage 2-4 で書いたエラーシナリオを動かす
- [ ] 実行中に詰まった箇所を全部書き出す

#### 7-2. 完了条件の計測
- [ ] Stage 2-3 で定義したレイテンシを計測する
- [ ] Stage 2-3 で定義したスループットをテストする
- [ ] 数値が満たされない場合は原因を特定する（Knuth の教え: 推測せず計測する）

#### 7-3. UX の確認
- [ ] 自分で実際に30分以上使ってみる
- [ ] ストレスを感じた箇所を全部書き出す
- [ ] インパクト順に並べて、上位から修正する

#### 7-4. 統合テストの追加
- [ ] コンポーネント間の連携をテストするケースを追加する
- [ ] 一部のサービスが落ちた場合の挙動をテストする
- [ ] データの整合性を確認するテストを書く

---

### Stage 8｜品質強化（75→85）「壊れない」

**完了条件**: 自分以外が使っても詰まらない状態

#### 8-1. エッジケースの網羅
- [ ] 「もし〇〇だったら」を10個考える（同時実行・大量データ・文字化け・タイムゾーン等）
- [ ] 各ケースに対してテストを書くか、対処するかを判断する

#### 8-2. セキュリティレビュー
- [ ] 入力バリデーション（SQLインジェクション・XSS・コマンドインジェクション）
- [ ] 認証・認可の確認（必要な箇所が守られているか）
- [ ] シークレット漏洩の確認（ログ・レスポンス・フロントエンドのコード）
- [ ] 依存パッケージの脆弱性スキャン（`npm audit` / `safety` / `trivy` 等）
- [ ] HTTPS / TLS の確認

#### 8-3. パフォーマンス計測と最適化
- [ ] プロファイラでボトルネックを計測する（推測ではなく計測）
- [ ] O(n²) になっている処理がないかを確認する（Knuth の教え）
- [ ] ボトルネックになっている箇所だけを最適化する
- [ ] 最適化前後の数値を記録する

#### 8-4. コードレビュー
- [ ] 偉人エージェント（Fowler / Uncle Bob / Lamport / Knuth）でレビューする
- [ ] または「1週間後の自分がわかるか」の目線で自己レビューする
- [ ] 指摘された項目を修正または記録する

#### 8-5. ドキュメント整備
- [ ] README: セットアップ・起動・よく使うコマンド
- [ ] アーキテクチャドキュメント（コンポーネント図・データフロー）
- [ ] トラブルシューティングガイド（よくあるエラーと対処法）
- [ ] CHANGELOG の開始

---

### Stage 9｜リリース（85→95）「世界に出す」

**完了条件**: 本番で動いており、問題が起きたときに検知・対処できる

#### 9-1. デプロイ手順の文書化
- [ ] ゼロからデプロイする手順を step-by-step で書く
- [ ] チェックリスト形式にする（抜け漏れが起きないように）
- [ ] 実際にその手順を1回なぞって検証する

#### 9-2. 本番環境の構築
- [ ] インフラの構築（サーバー / コンテナ / サーバーレス）
- [ ] ドメイン・証明書の設定
- [ ] 環境変数・シークレットの設定
- [ ] データベースのマイグレーション実行

#### 9-3. モニタリングの設定
- [ ] エラー監視（Sentry / CloudWatch 等）
- [ ] レイテンシ・稼働率の計測
- [ ] アラートの設定（閾値を超えたら通知）
- [ ] ダッシュボードの作成

#### 9-4. ロールバック手順の確認
- [ ] 前バージョンへの戻し方を確認する
- [ ] データのバックアップを確認する
- [ ] ロールバック手順を実際に試す（本番前に staging で）

#### 9-5. 初回リリース
- [ ] 最小限の機能でリリースする（全機能を一度に出さない）
- [ ] 限定ユーザー（まず自分）に公開する
- [ ] リリース直後に動作確認する

---

### Stage 10｜改善サイクル（95→100）「育てる」

**完了条件**: 終わりはない。ここから先はずっとこのサイクル

#### 10-1. フィードバック収集の仕組み化
- [ ] 使用データの収集設定（どの機能が使われているか）
- [ ] ユーザーへのフィードバック収集方法を決める（フォーム・インタビュー・アナリティクス）
- [ ] 定期レビューの頻度を決める（週次 / 月次）

#### 10-2. 改善の優先順位付け
- [ ] フィードバックをバックログに積む
- [ ] インパクト × コストで評価する
- [ ] 次に作るものを決めて Stage 2 からやり直す

#### 10-3. 定期的なリファクタリング
- [ ] 技術的負債を可視化する（コメント・TODO・複雑度）
- [ ] 計画的にリファクタリングの時間を確保する（Fowler の教え）
- [ ] リファクタリングはテストがある箇所だけ行う

#### 10-4. 依存関係の更新
- [ ] 依存パッケージを定期的に更新する（月次推奨）
- [ ] セキュリティパッチは即座に適用する
- [ ] 更新後はテストが通ることを確認する

#### 10-5. ドキュメントの維持
- [ ] 実装が変わったらドキュメントも変える（同じ PR で）
- [ ] 古くなったドキュメントを削除する
- [ ] CHANGELOG を更新し続ける

## このテンプレートの使い方

1. 新規プロジェクト開始時に `docs/project/phases.md` としてコピーする
2. 各タスクをプロジェクト固有の具体的なタスクに書き換える
3. 不要なタスクは削除する（全部やる必要はない）
4. 完了条件は必ず具体的な数値・状態で書き直す

---

## 基本的な考え方

Claude Code での開発は「Claude を優秀なジュニアエンジニアとして使う」感覚。
自分は**プロダクトマネージャー兼アーキテクト**として振る舞い、「何を・なぜ」を決める。
「どう実装するか」は Claude に任せる。

**アーキテクチャ・セキュリティ・重要なロジックは人間が決める。**

---

## フェーズ設計の原則

### 最初に固めること
1. 誰が使うか（個人 / チーム内 / プロダクト化）→ スケール・認証・コスト設計が変わる
2. 何で動かすか（Web / ネイティブ / CLI）→ 技術選定の前提
3. MVPの定義 → 「これが動けば Phase 0 完了」を言語化する

### フェーズの切り方
- Phase 0: 動く PoC（最小限で核心的な技術を検証）
- Phase 1: コア機能（実際に使えるレベル）
- Phase 2: 品質・UX（使いたくなるレベル）
- Phase 3: スケール・運用（他者に渡せるレベル）

**Phase 0 の完了条件を最初に言語化することが最重要。**

---

## タスク管理の方法

### ドキュメント駆動
- ユーザーへのアクション・確認事項はチャットではなくドキュメントに書く（チャットは流れる）
- フェーズとタスクは `docs/project/phases.md` で一元管理
- 決定事項・選定理由は `docs/project/overview.md` に残す

### セッションの使い方
- 1セッション1テーマ（複数の無関係タスクを混ぜない）
- セッション開始時に「今日やること」を宣言する
- セッション終了時に未完了タスクを phases.md に反映する

## Git 運用

### ブランチ戦略
- main: リリース可能な状態のみ
- feature/{機能名}: 機能開発
- fix/{バグ名}: バグ修正

### コミット規約（Conventional Commits）
```
feat: 新機能
fix: バグ修正
docs: ドキュメントのみ
chore: ビルド・設定等
refactor: リファクタリング
test: テスト追加・修正
```

### ルール

## Claude との効果的な対話パターン

### 実装依頼の型
```
【目的】〇〇を実装したい
【前提】現在の状態は〇〇
【制約】〇〇は禁止
【完了条件】〇〇が動けば完了
まずプランだけ書いて、実装はまだしないで
```

### 詰まったときのリセット
同じ間違いを2回繰り返したら `/clear` してプロンプトを書き直す。
コンテキストに失敗アプローチが蓄積しているのが原因。
