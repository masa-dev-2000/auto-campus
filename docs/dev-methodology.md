# 開発プロジェクトの進め方ノウハウ

Claude Code を使ったプロジェクト開発の方法論。随時更新する。

---

## 0→100 タスクテンプレート

どのプロジェクトにも適用できる抽象化されたタスク一覧。
新規プロジェクト開始時にこれをコピーして具体化する。

---

### Stage 1｜探索（0→10）「何を作るか」を決める

目的: 作る前に「作る価値があるか」「作れるか」を確認する。

- [ ] **問いの定義**: 「誰の、どんな状況での、どんな困りごとを解決するか」を1文で書く
- [ ] **オーナーの目的整理**: このプロジェクトで自分が得たいものを列挙する（学習 / 実益 / 実績 など）
- [ ] **競合・先行事例調査**: 同じ問題を解こうとしているものを探す。なぜ既存で足りないかを言語化する
- [ ] **技術的実現可能性の確認**: コアな技術的リスクを1つ特定し、それだけを先に試す（スパイク）
- [ ] **スコープの境界を引く**: 「作らないもの」を明示する。ないと際限なく広がる

**完了条件**: 「このプロジェクトは〇〇のために△△を作る。□□は作らない」と言える状態

---

### Stage 2｜定義（10→20）「何を作るか」を固める

目的: 曖昧さを全部つぶす。後から仕様変更が起きるのは、ここが甘いから。

- [ ] **コア機能の列挙**: MVP（最小で価値を届けられるもの）に必要な機能だけ書く
- [ ] **各機能の完了条件定義**: 「動いた」ではなく「〇〇したとき△△が起きる」という形で書く
- [ ] **非機能要件の定義**: レイテンシ・同時接続数・データ保持期間など数値で書く
- [ ] **使用シーンの具体化**: ユーザーが実際に使う場面を1つ詳細に描写する（ユーザーストーリー）
- [ ] **モード・状態の洗い出し**: システムが取りうる状態と、その遷移を図で書く（Lamport の教え）
- [ ] **未決定事項の列挙**: 決まっていないことを全部書き出す。決定を後回しにする場合はその理由も書く

**完了条件**: 仕様書（SPEC.md）ができており、Claude にそれを渡せば実装できる状態

---

### Stage 3｜設計（20→30）「どう作るか」を決める

目的: コードを書く前にアーキテクチャを固める。ここで妥協すると後で全部書き直す。

- [ ] **技術スタック選定**: 各レイヤーの選択肢を比較し、選定理由を記録する
- [ ] **コンポーネント分解**: システムをどう分割するかを図で描く（境界・インターフェース・依存の方向）
- [ ] **データモデル設計**: 扱うデータの構造・型・ライフサイクルを定義する
- [ ] **API / インターフェース設計**: コンポーネント間の契約（入出力の型・エラーケース）を定義する
- [ ] **リスク評価**: 技術的に怪しい箇所を列挙し、対策を決める
- [ ] **ディレクトリ構成の決定**: プロジェクトのフォルダ構成を決め、各フォルダの責務を書く

**完了条件**: コンポーネント図・データモデル・API 仕様が文書化されている

---

### Stage 4｜環境構築（30→40）「作れる状態」を整える

目的: 開発中に環境の問題で止まらないようにする。

- [ ] **リポジトリ初期化**: git init・CLAUDE.md・.gitignore・.env.example
- [ ] **パッケージ管理の設定**: 言語ごとのパッケージ管理ツールの初期化と依存の記録
- [ ] **開発用コマンドの整備**: start / test / lint / build を1コマンドで実行できるようにする（Makefile 等）
- [ ] **Lint・フォーマッターの設定**: コードスタイルを自動統一する仕組みを入れる
- [ ] **テスト基盤の準備**: テストランナーを選定し、最初のテストを1本書く（基盤が動くことを確認）
- [ ] **CI の設定**: PR 時に lint・test が自動で走る設定を入れる
- [ ] **シークレット管理の確立**: API キー等を安全に扱う方法を決め、誤コミット防止を設定する
- [ ] **CLAUDE.md にコマンドを追記**: 開発コマンドを全部書く

**完了条件**: `make dev` で動いて `make test` でテストが通る状態

---

### Stage 5｜PoC（40→50）「コアが動く」を確認する

目的: 一番難しい部分だけを先に作って、実現できることを証明する。

- [ ] **コアリスクの特定**: このシステムで「これが動かなければ全部無意味」な技術的核心を1つ選ぶ
- [ ] **最小スパイク実装**: 核心部分だけを動かす最小限のコードを書く（UI なし・エラー処理なし・ハードコード可）
- [ ] **実測による検証**: 完了条件（レイテンシ・精度等）を実際に計測する
- [ ] **判断**: 続けるか・スタックを変えるか・スコープを変えるかを決める

**完了条件**: 「この技術で作れる」が証明されている。または代替策に切り替えている

---

### Stage 6｜コア実装（50→65）「使えるものができる」

目的: PoC を本物のコードに育てる。設計原則を守りながら。

- [ ] **コンポーネントごとに実装**: 設計で決めた境界通りに1つずつ実装する
- [ ] **各コンポーネントに単体テストを書く**: 実装と同時に書く。後回しにしない
- [ ] **インターフェースの結合**: コンポーネントを繋いで動作確認する
- [ ] **エラーケースの実装**: 正常系が動いたら異常系（タイムアウト・接続失敗・不正入力）を実装する
- [ ] **ログの整備**: 何が起きているかを後から追えるようにする

**完了条件**: 設計書通りのコンポーネントが揃い、単体テストが通っている

---

### Stage 7｜統合・実用化（65→75）「実際に使える」

目的: 部品を組み合わせ、実際の使用シーンで動くことを確認する。

- [ ] **エンドツーエンドのシナリオ実行**: Stage 2 で書いたユーザーストーリーを実際に動かす
- [ ] **完了条件の計測**: Stage 2 で定義した非機能要件（レイテンシ等）を計測して満たすことを確認する
- [ ] **UX の確認**: 実際に自分で使ってみて、ストレスを感じる箇所を書き出す
- [ ] **統合テストの追加**: コンポーネント間の連携をテストするケースを追加する

**完了条件**: 実際の使用シーンで、完了条件を満たして動く

---

### Stage 8｜品質強化（75→85）「壊れない」

目的: 本番・他者利用に耐えられる品質にする。

- [ ] **エッジケースの洗い出し**: 「もし〇〇だったら」を10個考えて、対処する
- [ ] **セキュリティレビュー**: 入力バリデーション・認証・シークレット漏洩・依存パッケージの脆弱性
- [ ] **パフォーマンス計測**: ボトルネックをプロファイラで特定し、必要なら最適化する（Knuth の教え）
- [ ] **コードレビュー**: 自分以外の目（または偉人エージェント）でコード品質を確認する
- [ ] **ドキュメント整備**: 使い方・設定・トラブルシューティングを書く

**完了条件**: 自分以外が使っても詰まらない状態

---

### Stage 9｜リリース（85→95）「世界に出す」

目的: 安全・確実に本番環境に届ける。

- [ ] **デプロイ手順の文書化**: 誰でも同じ手順で本番に出せるようにする
- [ ] **本番環境の構築**: インフラ・ドメイン・証明書・環境変数の設定
- [ ] **モニタリングの設定**: エラー・レイテンシ・使用量を監視できるようにする
- [ ] **ロールバック手順の確認**: 問題が起きたとき、前のバージョンに戻せることを確認する
- [ ] **初回リリース**: 小さく出す。全機能を一度に出さない

**完了条件**: 本番で動いており、問題が起きたときに検知・対処できる

---

### Stage 10｜改善サイクル（95→100）「育てる」

目的: 使いながら良くし続ける。ソフトウェアは出した後が本番。

- [ ] **フィードバック収集**: 実際の使用データ・ユーザーの声を集める仕組みを作る
- [ ] **改善の優先順位付け**: 集まったフィードバックをインパクト × コストで評価する
- [ ] **定期的なリファクタリング**: 技術的負債を計画的に返す（ファウラーの教え）
- [ ] **依存関係の更新**: ライブラリのバージョンを定期的に更新する
- [ ] **ドキュメントの更新**: 実装が変わったらドキュメントも変える

**完了条件**: 終わりはない。ここから先はずっとこのサイクル

---

## このテンプレートの使い方

1. 新規プロジェクト開始時に `docs/project/phases.md` としてコピーする
2. 各タスクをプロジェクト固有の具体的なタスクに書き換える
3. 不要なタスクは削除する（全部やる必要はない）
4. 完了条件は必ず具体的な数値・状態で書く

---

## 基本的な考え方

Claude Code での開発は「Claude を優秀なジュニアエンジニアとして使う」感覚。
自分は**プロダクトマネージャー兼アーキテクト**として振る舞い、「何を・なぜ」を決める。
「どう実装するか」は Claude に任せる。

**アーキテクチャ・セキュリティ・重要なロジックは人間が決める。**

---

## フェーズ設計の原則

### 最初に固めること
1. 誰が使うか（個人 / チーム内 / プロダクト化）→ スケール・認証・コスト設計が変わる
2. 何で動かすか（Web / ネイティブ / CLI）→ 技術選定の前提
3. MVPの定義 → 「これが動けば Phase 0 完了」を言語化する

### フェーズの切り方
- Phase 0: 動く PoC（最小限で核心的な技術を検証）
- Phase 1: コア機能（実際に使えるレベル）
- Phase 2: 品質・UX（使いたくなるレベル）
- Phase 3: スケール・運用（他者に渡せるレベル）

**Phase 0 の完了条件を最初に言語化することが最重要。**

---

## 競合調査の進め方

新規プロジェクト開始時に必ずやる。

### 調べること
1. 既存ツールが「何をするか」と「何をしないか」
2. ギャップ分析（自分のプロダクトが埋める穴）
3. 技術選定のオプション（API / ライブラリ / OSS参照実装）
4. 主要なリスク（技術的・競合・ユーザー信頼）

### 参考：このプロジェクトの競合調査結果
→ docs/project/overview.md 参照

## タスク管理の方法

### ドキュメント駆動
- ユーザーへのアクション・確認事項はチャットではなくドキュメントに書く（チャットは流れる）
- フェーズとタスクは `docs/project/phases.md` で一元管理
- 決定事項・選定理由は `docs/project/overview.md` に残す

### セッションの使い方
- 1セッション1テーマ（複数の無関係タスクを混ぜない）
- セッション開始時に「今日やること」を宣言する
- セッション終了時に未完了タスクを phases.md に反映する

## 技術選定の記録方法

なぜその技術を選んだかを残す。後で「なぜこうしたんだっけ」が発生するのを防ぐ。

```
### [技術名]
- 選定理由:
- 代替案:
- 懸念点:
- 参考:
```

→ このプロジェクトの選定理由は docs/project/overview.md 参照

## Git 運用

### ブランチ戦略
- main: リリース可能な状態のみ
- feature/{機能名}: 機能開発
- fix/{バグ名}: バグ修正

### コミット規約（Conventional Commits）
```
feat: 新機能
fix: バグ修正
docs: ドキュメントのみ
chore: ビルド・設定等
refactor: リファクタリング
test: テスト追加・修正
```

### ルール
- コミットは1ファイル1コミットを基本とする（先人の知恵）
- main への直接プッシュ禁止
- テスト未実行でコミットしない（テスト整備後）
- git push は手動（意図しない push 事故を防ぐ）

## Claude との効果的な対話パターン

### 実装依頼の型
```
【目的】〇〇を実装したい
【前提】現在の状態は〇〇
【制約】〇〇は禁止
【完了条件】〇〇が動けば完了
まずプランだけ書いて、実装はまだしないで
```

### レビュー依頼の型
```
以下の観点でレビューして:
- セキュリティ
- パフォーマンス
- 可読性
変更は加えないで、指摘だけして
```

### 詰まったときのリセット
同じ間違いを2回繰り返したら `/clear` してプロンプトを書き直す。
コンテキストに失敗アプローチが蓄積しているのが原因。

## チェックリスト：新機能を追加するとき

- [ ] 完了条件を言語化した
- [ ] プランを Claude に書かせてレビューした
- [ ] 実装後にテストが通ることを確認した
- [ ] CLAUDE.md に追記が必要な規約・禁止事項はないか確認した
- [ ] phases.md のタスクを完了済みに更新した
